You have to either use a plain old integer or add a flag mechanism.Nothing in the C Standard suggests that unions have active members.  Instead, any action which is performed on any member of a union is simultaneously performed on all members that use the same storage.  The notion of unions having "active members" is a result of compiler writers trying to apply the "Effective Type" rules (which are so ambiguously written as to be worse than useless) to unions, despite that fact that unions and their members have declared types.
On a non-obtuse implementation for a platform which uses common floating-point types, given a union like:
union UF {
  uint32_t u;
  float f;
} uf;

the effect of writing 1.0f to uf.f and then reading uf.u would be to take the sequence of bytes associated with 1.0f [hex 00 00 00 40], IIRC and interpret that as a uint32_t, yielding 0x40000000.  Incrementing that and writing it back would cause the union to hold the byte sequence 01 00 00 40, and reading u.f would then yield the float value associated with that bit pattern, i.e. 1.00000006f.
At any point in time, both uf.f and uf.u will have values, and on a quality general-purpose implementation, the state of the universe after writing 1.00000006f to uf.f would be the same as the universe after writing 0x40000001 to uf.u.  It's thus not possible to print out the value of the last member of the union that was written unless one has manually kept track of which member that was.
Note that there are many situations--this among them--where the Standard makes no attempt to forbid "conforming" implementations from behaving in obtuse or useless fashion.  According to the Standard, any attempt to access uf.f or uf.u would invoke UB, since such an access would use an lvalue of type float or uint32_t to access an object of type union UF, an obtuse implementation could process such accesses in any fashion it sees fit.
The maintainers of gcc and clang have invented a concept of "active union member" modeled after the Effective Type rules, and may not recognize attempts to read or take the address of union members other than the active one.  Reliably tracking active union members is no more practical for a compiler than tracking Effective Types, however, and their behavior in practice ends up only being conforming to the extent that the Standard imposes no requirements on code that uses any union members of non-character types.There is no way you can use a struct or union identifier alone to get a value. Rule of thumb: If you
dup2()
one end of a pipe to standard input or standard output, close both of the
original file descriptors returned by
pipe()
as soon as possible.
In particular, you should close them before using any of the
exec*()
family of functions.
The rule also applies if you duplicate the descriptors with either
dup()
or
fcntl()
with F_DUPFD
In your code, you create all the pipes before you fork any children; therefore, each child needs to close all the pipe file descriptors after duplicating the one or two that it is going to use for input or output.
The parent process must also close all the pipe descriptors.
Also, the parent should not wait for children to complete until after launching all the children. In general, children will block with full pipe buffers if you make them run sequentially. You also defeat the benefits of parallelism.  Note, however, that the parent must keep the pipes open until it has launched all the children — it must not close them after it launches each child.
For your code, the outline operation should be:

Create N pipes
For each of N (or N+1) children:


Fork.
Child duplicates standard input and output pipes
Child closes all of the pipe file descriptors
Child executes process (and reports error and exits if it fails)
Parent records child PID.
Parent goes on to next iteration; no waiting, no closing.

Parent now closes N pipes.
Parent now waits for the appropriate children to die.

There are other ways of organizing this, of greater or lesser complexity.  The alternatives typically avoid opening all the pipes up front, which reduces the number of pipes to be closed.
'Appropriate children' means there are various ways of deciding when a pipeline (sequence of commands connected by pipes) is 'done'.

One option is to wait for the last command in the sequence to exit.  This has advantages — and is the traditional way to do it.  Another advantage is that the parent process can launch the last child; the child can launch its predecessor in the pipeline, back to the first process in the pipeline.  In this scenario, the parent never creates a pipe, so it doesn't have to close any pipes.  It also only has one child to wait for; the other processes in the pipeline are descendents of the one child.
Another option is to wait for all the processes to die(1).  This is more or less what Bash does.  This allows Bash to know the exit status of each element of the pipeline; the alternative does not permit that — which is relevant to set -o pipefail and the PIPEFAIL array.
