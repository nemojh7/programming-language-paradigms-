What the spec says
If you declare static objects inside a function then they exist and retain their values for the entire lifetime of the program.  There is only one copy of each such variable, regardless of how many times the function is called, and regardless even of concurrent and recursive calls.
If you declare non-static objects inside a function then each executaion of the innermost containing block gets its own copy of each one, and each such copy ceases to exist when the block execution with which it is associated terminates.
What you may see in practice
C implementations are allowed in many respects to deviate from the details of the specification as long as they produce the same observable behavior as if they had followed the spec to the letter.  Among the variances you might see are

If the compiler determines that a given function cannot ever be called, then the whole function may be omitted, along with any variables it declares.
If the compiler determines that a given variable cannot ever read then then the variable and any writes to it might be omitted altogether (unless it's volatile).
In principle, a program might not allocate or initialize static variables until they are first accessed (though this is unlikely).
Tail-recursive function calls may be collapsed into iterations, such that the function's local variables are re-used instead of new ones being created for each recursive call.

304 Status Code
The 304 status code is not an error, as indicated here:

A conditional GET or HEAD request has been received and would have resulted in a 200 OK response if it were not for the fact that the condition evaluated to false.

In this context it means that the Firefox browser sent an (ETag header](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/ETag) and basically said "send me the file only if the file was updated (it's ETag is different)".
Since the file wasn't updated, facil.io responded with an empty 304 response, indicating that the file wasn't updated.
At that point, Firefox displayed the file it previously cached instead of downloading the same data all over again.

Thanks for helping!You are tormenting yourself to no end attempting to coordinate the different data types between multiple arrays syncing names to scores by array index. While that is doable with 2-values, it will wildly spin out of control and become unmanageable. Instead, whenever you need to coordinate multiple values of different types as a single object in C, you should be thinking struct.
Here, if you define a simple struct to hole the players name, an array of scores and then a counter for the number of scores stored for that player, you can simply declare an array of struct for the players in your program and read data into each struct for your players. That way the name and as many scores as needed are coordinated in a single struct for each player. For example, you could declare your struct similar to:
/* if you need a constant, #define them or use an enum */
enum { NSCORES = 10, MAXNAME = 64, NPLAYER = 128, MAXLINE = 256 };

typedef struct {                /* simply struct for a player */
    char name[MAXNAME];         /* using a typedef for convenience */
    int ns, scores[NSCORES];    /* ns tracks the number of scores */
} player_t;

(note: the typedef provides a simple convenience in not having to type struct before the name everywhere the struct is used)
You could then read each line into a buffer using fgets() or POSIX getline() and then parse the name and the scores for each player from the buffer. You can use a number of methods to split the values in your buffer into the name and as many cores as are provided. In this case, with simple first names, it is probably just as easy to use sscanf() and keep an offset of your position in the buffer for reading all remaining scores. 
(your other alternative for splitting the line into values are to use a pair of pointers to bracket each value for extraction, use the strtok() function (or strsep()) to tokenize the line, or a combination of pointers with strchr(), strspn() and strcspn() -- up to you)
You can use fgets() to read the line and sscanf() to separate value similar to:
int main (void) {

    char buf[MAXLINE];          /* buffer to read entire line of input */
    size_t n = 0;               /* counter for number of players read */
    player_t player[NPLAYER] = {{ .name = "" }};    /* array of players */

    /* while array not full, read each line of input into buf */
    while (n < NPLAYER && fgets (buf, MAXLINE, stdin)) {
        int offset;     /* to keep offset from beginning of buf */
        /* read name from buf, save no. of chars read in offset */
        if (sscanf (buf, "%s%n", player[n].name, &offset) == 1) {
            int chars;  /* to track characters consumed for each score */
            /* read score, save no. of chars read */
            while (player[n].ns < NSCORES && sscanf (buf + offset, "%d%n",
                    &player[n].scores[player[n].ns], &chars) == 1) {
                offset += chars;    /* update offset with chars read */
                player[n].ns++;     /* update no. of scores for player */
            }
        }
        if (player[n].ns)       /* if scores stored for player */
            n++;                /* increment player index to next player */
    }

(note: the characters consumed reading name are stored directly in offset (as there is no offset at that point), but then the number of character read to convert each digit are stored in chars so it can be added to the current offset for the next read)

In order to not have any overlap given whatever length of the word which is used by the architecture (32 bit or 64 bit or any other bit) you may not declare more flags than there are bits in the word length. Also, each flag in the enumeration must be included in the range of 2^n where n ranges from 0 to the length of the word (32 bit or 64 bit).
This enumeration is only necessary so long as you expect to use a single variable to store multiple flags through the use of the bit wise OR operator "|". Since the bit wise OR operator will only be able to distinguish between unique states that cannot be derived through adding them together, as shown in the original question.
This is useful in having styles for text such as bold, italics and underlined. In one variable you can determine whether it has one or any of these styles so long as their enumeration follows the pattern of 2^n for each style.

However it is possible to store up to "n" number of states which corresponds to the length of the word of the architecture as previously stated within a single variable if you follow the pattern for that usage.Each bit can only have one of two possible values: 0 or 1. This applies universally, regardless of the programming language.
However, this doesn't mean that your machine's word size limits the number of flags you can have: you can just use more than one word (e.g., on a 32-bit machine you could have an array of 32-bit integers that you access like flags[n / 32] & (1 << (n % 32))). So, what could be done differently when writing such a program?
First using random values in code is a bad idea. The consequence is that the code behavior can't be repeated from one run to the next one. 
It is also important that the code clearly separate user inputs (data) and code manipulating that data.
In that case, it means that the createLinkedList() function should probably have another signature. Probably something like node *createlinkedList(int num, int data[]) where the data[] array will contains values to sort. It is still possible to fill input data with random values if it is what we want.
