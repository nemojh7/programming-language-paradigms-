Any decent compiler should have warned you about this such as with the gcc warning:
FILE *fp = ("Hello.txt","w");
           ^
warning: initialization from incompatible pointer type

and I often compile with the -Werror flag so as to have the compiler treat warnings as errors, to catch precisely this sort of thing.

You may actually be wondering why the compiler considers this just a warning but the truth is that it's perfectly valid code. The parentheses around an expression are valid which is why you can write either x = 7 or x = (7), or even x = (((((7))))), and have it mean the same thing.
What remains then is just the expression within the parentheses, and this uses the C comma operator. Basically, the expression a, b evaluates a (discarding the result) then evaluates b and uses that as the result of the expression.
You can verify this behaviour with the following program, which outputs w:
#include <stdio.h>
int main (void) {
   char *fp = ("Hello.txt", "w");
   puts (fp);
   return 0;
}

for (i = 0, j = 0; i < 100; i++, j += 2)
    printf ("%d x 2 = %d\n", i, j);

In situations like that, it's fine to throw away the result of the sub-expressions since you're simply relying on the ++ side effect of evaluation.

FILE *fp = ("Hello.txt","w");

}Is read() on a nonblocking socket "greedy" on platforms other than Linux (OSX, FreeBSD)?Consider the following invocation of read() on a nonblocking stream-mode socket (SOCK_STREAM):
ssize_t n = read(socket_fd, buffer, size);

Assume that the remote peer will not close the connection, and will not shut down its writing half of the connection (the reading half, from a local point of view).
On Linux, a short read (n > 0 && n < size) under these circumstances means that the kernel-level read buffer has been exhausted, and an immediate follow-up invocation would normally fail with EAGAIN/EWOULDBLOCK (it would fail unless new data manages to arrive in between the two calls).
In other words, on Linux, an invocation of read() will always consume everything that is immediately available provided that size is large enough.
Likewise for write(), on Linux a short write always means that the kernel-level buffer was filled, and an immediate follow-up invocation is likely to fail with EAGAIN/EWOULDBLOCK.

Question 2: Is this also guaranteed on FreeBSD?
Question 3: Is this required/guaranteed by POSIX?
