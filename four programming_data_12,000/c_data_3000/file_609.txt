Some people suggest using non-blocking sockets here but the I/O multiplexing APIs inform you anyway if there is data to read so what is wrong with a blocking socket here?If your TCP server is single-threaded and uses blocking I/O, then it's likely that any client that connects to it will be able to deny service to all of the other clients simply by sending only a partial-message, or alternatively by refusing to read any data from its TCP socket after the server sends data.  In the former case, the server may block for a long time (perhaps forever) waiting for the entire message to be received from the client; during that time, the server will not be able to respond to other clients.  In the latter case, the server will block for a long time (perhaps forever) waiting the client to read some TCP data so that the server-socket's send-buffer can be drained enough to fit some more outgoing data to that client.
One way to avoid that problem is to set all of the server's sockets to non-blocking I/O mode; that way the server knows it can never get "stuck" inside a recv() or a send() call, and thus can remain responsive to all clients regardless of whether any particular client is behaving nicely, or not.   In the non-blocking design, the only place the server ever blocks is inside select() or poll() or similar, because those calls are designed to return whenever any client needs service, rather than blocking on only a single client.   (the tradeoff is that with non-blocking I/O your server's buffering/queueing logic will need to be a bit more elaborate, since you can no longer assume that any particular fixed number of bytes will be sent or received during any given send or receive operation)
The other way to avoid the problem is to make a multi-threaded server; that has the advantage that each client gets its own thread, and therefore a badly-behaved client will block only its own thread and not the threads servicing other clients.  The disadvantage is that now your server is multi-threaded, with all of the additional pitfalls that multithreading introduces.
(and, for completeness, the third approach is simply to ignore the possibility of badly-behaved/poorly-connected clients, and use a single-threaded/blocking model. So in order to see if we are allowed to do pass something to a function, we need to check the rules for assignment. Among the rules for simple assignment, all valid forms are listed, including this one (6.5.16.1, emphasis mine):

That depends on how you define "simple".
You will need to parse the link-layer header to determine whether the packet is an IPv4 packet or not.  If it is an IPv4 packet, you will need to parse the IPv4 header to see if either 1) the "More Fragments" bit is set in the "Flags" field or 2) the "Fragment Offset" field is non-zero.  If either of those are true, it's an IPv4 fragment.

and defragment this packet with C code?

You will need a table indexed by IPv4 source and destination addresses and "Identification" field value.
For each fragmented IPv4 packet, look in that table to see if you find an entry with the same IPv4 source and destination addresses, and same Identification field value, as the ones in the fragmented packet's header.
If you don't find it, add an entry to the table, and save the contents of the packet in that entry.  If the Fragment Offset value is 0, save the entire IPv4 header, as well as the packet payload, along with its Fragment Offset value, payload length, and More Fragments flag (yes, that's redundant, as you have the full header, but you did ask for a simple way :-)); otherwise, just save the payload, along with its Fragment Offset value, payload length and More Fragments flag.
If you do find it, then, if the Fragment Offset value is 0, add the IPv4 header to the entry.  Then, regardless of the Fragment Offset value, add the packet payload, with its Fragment Offset value, payload length, and More Fragments flag, to the saved packet payload information.  This means that the entry has an IPv4 header and a set of packet payload/Fragment Offset value/payload length/More Fragments flag combinations.
For each fragment you add, after you've added it, check to see whether:

if you sort the fragments by their Fragment Offset value, for all but the last fragment, the Fragment Offset value plus the payload length of that fragment is equal to the Fragment Offset value of the next fragment;
the last fragment does not have the More Fragments flag set.

If that's true, you have all the fragments, and can reassemble them into an IPv4 packet whose header is the saved header from the first fragment (the one with a Fragment Offset value of 0) and whose payload is the concatenation of the payloads of all the fragments.
