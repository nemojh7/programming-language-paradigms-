A note on the malloc calls - in C, you do not need to cast the result of malloc, and doing so is generally considered bad practice1. Also, the operand to sizeof doesn't have to be a type name - it can be an expression of the type you want to allocate.  IOW, given a declaration like
T *p;

both sizeof (T) and sizeof *p do the same thing - the expression *p has type T.  So the general form of a malloc call can be written as
T *p = malloc( sizeof *p * N );

or
T *p;
...
p = malloc( sizeof *p * N );

That's simpler to write and easier to maintain than
p = (T *) malloc( sizeof (T) * N );

Hiding the pointer-ness of a type behind a typedef is bad juju, especially when the user of that type has to be aware that he or she is dealing with a pointer type. Similarly, if the user has to be aware of the struct-ness of the type, you shouldn't hide that struct-ness behind a typedef either.  
Abstraction is a powerful tool, but partial (leaky) abstractions like the original code just make life more confusing for everyone (as you have discovered for yourself).

For example, the final outcome of such initialization might depend on the order in which it is performed. The initialization might fail for some unpredictable reason (out of memory?). And, obviously, the values of SSD objects cannot be treated as constant expressions.
Meanwhile, in order to steer clear of such issues C language specification was consciously designed to avoid any need for dynamic initialization for SSD objects. For example, all such objects in C program are required to be initialized with constant values. Which means that the initial values of such objects are free from any initialization order dependencies and are conceptually "known at compile time". When a C program starts, all SSD  objects begin their lives with properly pre-assigned values, requiring no extra run-time initialization.
However, the reality is more complicated and it is not always possible to predict initial values of SSD objects at compile time. For example, address constants that describe locations of relocatable objects become known only at loading time, not at compile time, which generally makes it impossible to predict the values of SSD pointers at compile-time. The language specification is designed to accommodate such peculiarities. Properties of address constants in C are deliberately restricted to make it possible to initialize their values later, at loading time. In C this is considered a proper compromise in situation when the initial value is not known at compile time, and yet we still want to maintain the appearance of SSD objects beginning their lives in pre-initialized state.

All objects with static storage duration shall be initialized (set to
  their initial values) before program startup. The manner and timing of
  such initialization are otherwise unspecified.

Suppose your function is called with three arguments, an int, a double, and a long double. They might all have different sizes.
The va_arg mechanism deliberately hides the underlying layout of the variable parameters, because it can vary from one implementation to another.
But let's assume a typical implementation might pass arguments on the stack, one after the other. Your function would have no way of knowing where in memory the third long double argument is without knowing the sizes of the first two arguments. And the amount of space taken up by each argument might not match the size of that argument; for example it might be more convenient to allocate 64 bits for a 32-bit argument.
<stdarg.h> deliberately provides a fairly minimal interface for accessing variable arguments. It only lets you access them in order, and only if you know the type of each argument.
If you want to do something similar, you could write a function that takes a pointer to the initial element of an array of pointers, each if which points to some data structure that can hold any of several types (perhaps something like a tagged union). But then the caller has to set up that structure before calling the function.
