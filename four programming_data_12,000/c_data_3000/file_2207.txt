No one guarantees there's 0xAABBCCDD anywhere in the writable memory of the process. The compiler can optimize it away entirely, or put in in a register. One way to enssure a variable will be placed in the main memory is to declare it volatile.
volatile int x = 0xAABBCCDDEE;

No one guarantees there's no 0xAABBCCDD somewhere in the read-only memory of the process. On the contrary, one could be quite certain there is in fact such a value there. Where else could the program possibly obtain it to initialise the variable? The initialisation probably translates to an assembly instruction similar to this
mov eax, 0xAABBCCDD

which, unsurprisingly, contains a bit pattern that matches 0xAABBCCDD. The address 0x6005DF could well be in the .text section. It is extremely unlikely it is on the stack, because stack addresses are typically close to the top of the address space.

This code is make me crazy. It is a code built to solve mutual exclusion between the two programs (0 , 1). 
Can some one explain me how does the flag change for each program 0 and 1 when put into the code.The array of 2 booleans, flag, must be in shared memory for this to have a chance of working.  For processes, that is crucial; if these were threads, you'd not need shared memory.
Initially, neither process 0 or 1 has set its flag value to true.
Suppose process i = 0 tries to gain access to the critical section. The first busy loop (while loop) waits until flag[1] is false (and it is false at the moment); then the code sets flag[0] = true.  The code now enters the second busy loop; flag[1] is still false, so it goes ahead and enters the critical section safely, knowing that the other process is not in the critical section either.
Suppose that while process 0 is in the critical section, process 1 tries to enter it too.  It is blocked in the first busy loop because flag[0] is true.  It remains like that until process 0 leaves and sets flag[0] back to false.  When process 0 leaves, process 1 sets flag[1] to true, enters the second busy loop, and then leaves because flag[0] is false; it is now in the critical section.
Why the two busy loops?  Because it might happen that the two processes are running on multiple cores at the same time, and both might enter the first busy loop at the same time.  They would both see that the other's flag is false, exit the loop and set their own flag to true, and recheck that the other's is still false.  Most of the time, one of them would see that the other's is false and would enter the critical section.  Occasionally, they might both spot that the other's is true (because they were working so much in lock-step), and then both would enter the second busy-loop, and neither would exit — deadlock.
So, I'm not convinced that the code is a foolproof mutual exclusion mechanism, though it would require bad luck to get into deadlock.  However, given enough attempts, bad luck will occur — long-running processes can't afford the risk.
