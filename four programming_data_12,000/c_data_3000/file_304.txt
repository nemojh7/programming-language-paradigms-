It only determines the size of the type of its operand.
For example, if you allocate an array of 1000 int with int *x = malloc(1000 * sizeof(int));, then sizeof *x returns the size of one int, because the type of *x is int.
For sizeof *w, where w is a structure with a flexible array member, sizeof returns the size of the type, which is the base size of the structure. It does not know how much extra space you allocated for the structure.
The base size of the structure is the same as the size as if the structure had been defined without the flexible array member, except it may have more padding (which may be needed if the flexible array element type requires more alignment than other things in the structure).

          close(fd);
          return file_length;
        }

            char *b = buffer;

                     */
                     close(fd);
                     return file_length;
                  }
                else
                  {
                    file_length += write_length;
                    b += write_length;
                    read_length -= write_length;
                  }
              }
         }
    }

At the bottom of your code, you would first free the wine ratings for each member and then free the member list itself:
for (int i = 0; i < n; i++) {

In general, you should have a matching call to free for each call to malloc.
A little more explanation:
The first call to malloc allocates a single block of memory to hold n members' information. Even though this block of memory can store n members' information, it is still just a single block of memory and will be freed with a single call to free.
In your loop, you allocate a block of memory for each member (n times) that will store their wine ratings' information. Even if a member has many wine ratings, there is still just one block of memory for that member's wine ratings, so you'll need as many calls to free as there are members with wine ratings.
Also, notice how the calls to free happen in reverse order of the calls to malloc. In C, the arguments are passed by value, when you pass a pointer as an argument of a function, you are passing the value of the pointer, basically a copy of it, not the pointer itself, malloc will change the value of that pointer, but since what you passed was a copy, that is what's changed, not the original pointer, that one remains unchanged.

In the second code snippet, the working code, *elem = malloc(sizeof(int)); broadly means make this pointer elem point to this valid memory address given to me by malloc(assuming it succeeds), the value of the pointer to the pointer elem which you passed as an argument remains unchanged, it being a copy doesn't matter because it's not changed, it's still the same address that was passed as argument, the address of the pointer num which is now pointing to the memory location given by malloc.
**elem = num_value means store num_value in the address stored in the pointer where elem is pointing to, which is where num is pointing to, which is the new memory block previously given by malloc.

(Perhaps this question should be renamed to GDB attach causes laptop to freeze when ran with sudo on multi-threading program using fork(), thoughts appreciated!)The problem is that when several clients connect to the server, if many messages are sent to the server, there is not instantaneous delivery of messages to clients.

Your clients alternate between blocking on fgets(), waiting for input from stdin, and blocking on recv(), waiting for input from the server, so they'll only work if there's strict alternation between the two directions. A single call to recv() on a TCP socket can give you data written by multiple calls to send(), because TCP indeed is a byte stream, so you can get multiple messages at once (though you can't tell them apart). But fgets() gives you only one line at a time, if the client is waiting to receive something from the server, it wouldn't be able to read more input from stdin at the same time.

Perhaps there is an alternative to tracking client connections on server-side than with file.

Storing file descriptor numbers in a file doesn't seem to make any sense at all. Fd numbers are just small integers, and their meaning is different for different processes. They're not globally unique identifiers!
You're forking a new process for each incoming connection. Each child process will get a copy of the file descriptors the server has open at that time. So, the first child will get the fd for the first client connection, the second child will get the fd's for the first two client connections, etc. But none of the children will ever get fd's for clients that come later, so you should be getting a number of errors for every time they attempt to write to fd's read from the file.
Forking a single child for each connection really only works if the clients don't need to interact directly. Also your child processes seem to fall out to the end of the whole main function if they ever get to break out of the inner while(1), and the first to do so, will remove the clients.txt file. Even more, it looks like you're not paying any attention to the return values of the recv() calls, so if the remote closes the connection, you'll just spin forever on the recv(), which returns 0 marking "end of file".

Instead, you need to keep all the client fd's in a single server process, which can then read and write to/from all of them. Store their numbers in an array or such. Here, you're in the same situation as the client, you need to be able to monitor multiple fd's for input at the same time instead of blocking on one at a time. For that, you'll need to use select() (or poll(), or epoll()). The same goes for the client. There's an example for using select() in the GNU libc documentation: https://www.gnu.org/software/libc/manual/html_node/Server-Example.html

}This is a fundamental and important issue. You need to not only know how to handle dynamic allocation, but how to handle it in the structured way. To begin with, you need two counters. One counter tracking the number of integers you have allocated for and the second counter tracking the number of integers used. You do not need to reallocate when you "remove" an integer, only when adding and when used == allocated. Otherwise, if used < allocated, there is no need to allocate for the next integer following "add".
Ideally you want to allocate for some anticipated number of integers and only reallocate when you run out of space in the initially allocate block of memory (generally doubling the size of the currently allocated block each time reallocaion is needed) to minimize the number of relatively costly call to realloc()1. It does add a minor bit of complexity. For a learning exercise, allocating for each new int is fine.
One other note before looking at the allocation scheme is taking input with scanf().  That leads to a horribly fragile input scheme. One stray character in input will result in a matching-failure where the bad character is left unread in stdin breaking your next (and if you rely on input ordering -- the rest of your) inputs. It is far better to read input with a line-oriented input function (like fgets() or POSIX getline()) so that an entire line of input is consumed with each read. You can then parse the values you need from the buffer (character array) filled by fgets() using sscanf(). That way regardless of whether the conversion with sscanf() succeeds or fails, nothing is left unread in stdin.
Additionally, avoid the use of global variables. Instead, declare your variables in the scope where they are needed and then pass any needed information to a function as a parameter rather than relying on global variables. (they have their proper place -- but none you will find as you are learning C, unless you are programming on a microcontroller)
Now for your allocation scheme, changing your name of number_of_elems to allocated to track the number of integers allocated for and adding used to track the number of int used within your allocated block, your scheme would be:

initialize ptr = NULL; to begin,
after reading an "add" and using strcmp() to confirm (you compare string equality in C with strcmp(), not ==), you will read and VALIDATE the conversion of the integer that follows, then
compare if (used == allocated) to determine if allocation for a new integer is needed, if so
use realloc() for all allocations (realloc() behaves like malloc() when the pointer is NULL),
After you VALIDATE the allocation you increment allocated += 1; and after storing the integer value to the new block of memory, you increment used += 1;,
if "remove" is chosen, all that is needed is you VALIDATE used > 0 and if so, just decrement used, there is no need to adjust the allocation at this point -- that only happens with an "add".

                    break;                          /* don't exit, ptr still good */

Decide which header is "higher" and will include the "lower" and don't try to include the higher one from the lower one.  The lower one must be valid on its own.
The reason for this is that the pre-processor has to transform multiple files into one linear sequence of lines for the compiler.  The compiler has to see one set of file contents before the other.
If you have cyclic includes like this you make it up to the final user of the code which one comes first.  If they include file A, then it will include file B, which will try to include file A again but it will be prevented by the include guards, so the contents of B will be parsed first.  On the other hand if the final user includes B first, then the contents of A will be seen first by the compiler.
So if you leave it like it is, then it is effectively random which file gets included first.  If you break the cycle, you get to decide yourself which is included first.

    listen(s, 0);
    int t = accept(s, NULL, NULL);
    if (t < 0) perror("accept"), exit(1);
    fd_set fds, fdr;
    FD_ZERO(&fds);
    FD_SET(0, &fds);    // add STDIN to the fd set
    FD_SET(t, &fds);    // add connection to the fd set
    while (fdr = fds, select(t+1, &fdr, NULL, NULL, NULL) > 0)
    {   char buf[BUFSIZ];
        if (FD_ISSET(0, &fdr))
        {   // this is the user's input
            size_t count = read(0, buf, sizeof buf);
            if (count > 0) write(t, buf, count);
            else break; // no more input from user
        }
        if (FD_ISSET(t, &fdr))
        {   // this is the client's output or termination

            if (count > 0) write(1, buf, count);

        }
    }

This is not how MPI is meant to be used, actually parallelism in general IMO. The coordination of printing the output to the console among processes will greatly degrade the performance of the parallel version.
Most of the times one is better off just making one process responsible for printing the output to the console (typically the master process i.e., process with rank = 0).
Nonetheless, you can try something like the following with the MPI_Barrier, like so:
int rank;
MPI_Comm_rank (MPI_COMM_WORLD, &rank);  /* get current process id */
...
MPI_Barrier(MPI_COMM_WORLD);
if(rank == /** the rank of the process that will print the output **/)
{
   // printing the data to the output
}
MPI_Barrier(MPI_COMM_WORLD);
