Bit of background:
Note that "the strict aliasing rule" is not a formal term, but it refers the the paragraph 6.5/6 regarding effective type and 6.5./7 regarding accessing data through a pointer. The latter paragraph is the actual strict aliasing rule and it has been part of C for as long as the language has been standardized, so its existence should actually not come as a shock to anyone. The text in 6.5./7 is nearly identical all the way from the ANSI-C drafts to C11.
However, this section was unclear in C90, because it focused on the type of the pointer used for the "lvalue access", rather than the type of the data actually stored there. Which made situations where you cast to void pointers unclear, such as when using memcpy, or when you are doing various forms of type punning.
In C99 there was some attempt to clarify this by introducing effective type. This didn't actually change the wording of the strict aliasing rule much, just made the interpretation somewhat clearer. (It still remains one of the hardest parts in the standard to understand.) 
The original intent for the rule was to allow compilers to avoid weird worst-case assumptions, such as this example from the C99 rationale:
int a;
void f( double * b )
{
  a = 1;
  *b = 2.0;
  g(a);
}

If the compiler can assume that b is not pointing at a, which should be a sensible assumption to make given the wildly different types, then it can optimize the function to 
a = 1;
*b = 2.0;
g(1); // micro-optimization, doesn't have to load `a` from memory


So even though the rule has been there all the time, it wasn't a problem before somewhere along C99, when the gcc compiler in particular decided to go haywire and abuse the cases where different effective types were used. For example this code makes perfect sense, yet violates strict aliasing:
uint32_t u32=0;
uint16_t* p16 = (uint16_t*)&u32; // grab the ms/ls word (endian-dependent)
*p16 = something;
if(u32)
  do_stuff();

The above would be very useful code in all manner of bit-twiddling and hardware-related programming. Most compilers will generate what the programmer expects, namely code that changes the ms/ls word of the 32 bit value then check if the function should be called. 
However, since the above code is formally undefined behavior because of the strict aliasing violation, compilers like gcc might decide to abuse it and generate code that always removes the call to do_stuff() from the machine code, since it may assume that nothing in the code changes u32 from having the value 0.
To dodge that unwanted compiler behavior, the programmer has to go out of their way. Either make the u32 volatile so that the compiler is forced to read it - which blocks all optimizations on the variable and not just the undesired one. Or alternatively come up with a home-brewed union type containing one uint32_t and two uint16_t. Or possibly access the u32 byte per byte. Very inconvenient.

Therefore programmers tend to rebel against the strict aliasing rule and write code the relies on the compiler not making incredibly weird optimizations based on strict aliasing. There exists many valid cases when you want to break up a chunk of data in different parts, such as when de-serializing a block of raw data bytes. 
For example if I receive serial data byte-by-byte and store it in an array of uint8_t that I, the programmer, know contains a uint16_t, I should be able to write code like (uint16_t*)array without the compiler making assumptions such as "oh look, this array is never used, lets optimize it away" or some other nonsense.
Most compilers will not go crazy but generate the expected code. But they are allowed to go crazy by the standard. And with the growing popularity of gcc in hardware-related programming, this is becoming a serious problem for the embedded industry, where hardware-related programming is an everyday task, rather than an exotic special case.
Overall, the standard committee has repeatedly failed to see this problem.

Issues of aliasing don't really have anything to do with "programmer intent".  Outside of compiler testing or other contrived scenarios, programmers essentially never intend that code behave in a fashion inconsistent with the behavior produced by having all lvalue accesses operate upon underlying storage in execution order.  There are some application fields where such behavior would, for all practical purposes, always be equivalent to some other behaviors that could be realized more efficiently, and there are some application fields where the latter alternatives would be observably and disastrously different.

Anywhere where the 'owner' of a resource is changed can be interpreted as 'move semantics'.C doesn't have a direct equivalent to move semantics, but the problems that move semantics solve in c++ are much less common in c:

C also doesn't have destructors and the RAII pattern, so transferring ownership of a resource comes up less frequently.The C equivalent to C++ move semantics would be to pass a struct by value, and then to proceed with throwing away the original object without destructing it, relying on the destruction of the copy to be correct.
However, this is very error prone in C, so it's generally avoided. The closest to move semantics that we actually do in C, is when we call realloc() on an array of structs, relying on the bitwise copy to be equivalent to the original. Again, the original is neither destructed nor ever used again.
The difference between the C style copy and C++ move semantics is, that move semantics modify the original, so that its destructor may safely be invoked. With the C bitwise copy approach, we just forget about the contents of the original and don't call a destructor on it.

Thanks in advance.In case of global variables (also static local):
The compiler accesses global variables as memory parts of certain address and size. The address is initially a placeholder (much like the name of the variable). The size is implicit, depending on which kind of access the compiler has chosen in assembly/machine-code. The linker/loader is aware of the size, it makes sure that the next variable is not overlapping.
The address placeholder gets replaced during linking (e.g embedded, static, execute-in-place) or loading (e.g. programs on a PC, Apps).  
In case of local variables:
The "address" value, which gets written into the placeholder, is relative, an offset on "top" of the stack position at the time of starting the function.
It is otherwise determined like the values for the global placeholders. The position on the stack is influenced by which variable is accessed, optionally with a sub-offset for struct members. The actual address is determined as the stack position (i.e. value of stack pointer) plus the relative offset found in the placeholder.
The placeholders are actually lists of offsets, stored in a binary (e.g. a program.exe) along with the actual binary code. Something like "when you have decided where this variable is found in memory, then write the address in all the places within code which are listed here: ...". Writing to these places will for example put a meaningful value in a byte which during execution will be interpreted as a literal offset to a relative "MOV" assembler instruction; relative to e.g. a section pointer to start of BSS section.
So in short, the address information is in the lists of placeholders. These lists migth not be found in memory at all, or not at execution time. Once the program is loaded (including filling in the placeholders) these lists are not needed anymore.
The size information is part of the code (e.g. using 8bit access or 32bit access) and it is part of the layout of variable locations. Each gets accessed far enough behind the previous variable.
So, even shorter, the information you are looking for is half hidden and half not in memory at all during execution.

Just to cover it: The value gets initialised to either 0, a constant initialisation value or, special cases, not at all, keeping whatever is in the memory at startup. The init values are found in sections which are basically lists of constants. Where exactly the constant for a given variable is found is similar to the placeholders.
In case of local variables, the compiler usually does not initialise, but can be configured to write 0 (which is kind of "expensive"). In your question, you refer to "left" and "right", but as the variable "top" implies, it's easier visualising a vertical stack.
For example, imagine a stack of dinner plates.  New plates are always "push"ed onto the top, and on demand they are also "popped" from the top.
So as you can see, this sort of stack is called a Last-In-First-Out (or LIFO) stack, and this is what your code is implementing.
The s1->top variable is a pointer to the top of the stack - ie. the last node added, which will also be the first to be removed.  Each node also has a pointer to the next node "under" it.   NULL is used to indicate "no more nodes", both for s1->top, and the node->next pointers.
So in push(), two things must happen for consistency :

The new arrival's ->next pointer must be set to the current
"top" of the stack (so the existing top is "under" the new arrival),
and 
The new arrival must be set as the new "top".

Note that the order of operations here is important - if (2) was performed before (1), then you could end up with the new arrival's "->next" pointer pointing to itself !
pop() performs basically those operations in reverse, and display() simply runs down all the elements in the stack (notice that display() does NOT alter the value of s1->top ).I dont know wahts your problem,
