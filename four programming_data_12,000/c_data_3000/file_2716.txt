Your issue was that when you computed product = A * B * C * D * ... your intermediate results (A, B, ...) were of type int by default. The C standard states that multiplying two int's produces another int, it won't automatically upgrade itself to a bigger type if the value is too big. As such, the code was the same as:
int int_product = A * B * C * D * ...;
product = (unsigned long long int) int_product;

Which shows clearly why there would be such an error. To prevent the compiler from treating the intermediate results as ints you have 2 options:

Never store the intermediate results in the first place. 

This is the option I present below, where you never actually multiply two integers together, rather you always multiply the unsigned long long int with an int. The reason this works is that the C standard states that the int will be promoted to match the unsigned long long int. In general when there are two types of different sizes, the compiler will tend to promote the smaller one to match the larger one if necessary rather than the other way around. Based on this we can construct:

Convert one of the intermediate results to the appropriate sign to force integer promotion.

This is the option presented in the other answer. By changing the statement to:
product = (unsigned long long int) A * B * C * D * ...;

You force the coercion of A * B to be unsigned long long int which forces (A * B) * C to be the same, etc all the way until the end of the values.

In C, pointers and arrays are often interchangeable (though anyone saying that they're the same thing hasn't used C) — you can think of this because you can do arithmetic on a pointer to access adjacent data, and arrays are just stored as adjacent data. So you need a pointer to pointers to characters, or char **.
You need to think about exactly how your data is going to be stored in memory. In this case, you will want to have one inventory list that stores an array of pointers (pointers are fixed-length so this is fine). Each pointer will be a pointer to the actual string containing that item in the inventory.
Second, the inventory itself needs to be malloc'd, but if all of the strings you want to store in it are fixed at compile-time, the strings themselves don't have to be. If this is confusing to you, think of it this way — when you run the program it needs to be loaded into memory somewhere. So strings that were compiled into the program will exist somewhere in memory, and C will let you take a pointer to this string in memory just like you can take a pointer to variables in memory. So, every time you need to add a string to your inventory, you'll first want to resize your inventory by incrementing its size, creating a new inventory with the new size, using memcpy or similar to copy the existing contents of the inventory to the new copy, and then calling free on the old copy (very important otherwise you will get a memory leak, which are hard to spot but mean that if your program runs for long enough it will eventually eat all your RAM), before finally overwriting your pointer to the old copy with the pointer to the new copy.
Then, you'll want to put the string into the inventory by doing something like inventory[amount-1] = "some string"; (of course, the string could also be passed into a function as an argument, in which case it should be a variable of type char *).
If your strings aren't all fixed at compile-time (ie if you want to put someone's name in the inventory that they enter on the command-line, or if you want to have a number like "thing 1", "thing 2" etc. that is generated in a loop or something), then you'll need to malloc space for the string as well.

It looks like interrupt vector table used for embedded programming.This appears to be an interrupt vector table for an ARM Cortex M microcontroller.

One special feature in ARM Cortex compared to most other MCUs, is that it has the stack pointer set before program start. Other MCUs tend to set it in run-time.
So the very first entry in the table is the value which the stack pointer should be set to at program start-up. __STACK_END is likely some constant obtained from the linker. The cast (void (*) (void)) turns it into a function pointer. Casting from a pointer to an int to a function pointer is a bit questionable, but it will likely work on most embedded C compilers, despite the C standard frowning at such.
The rest of the entries are function addresses to interrupt service routines (functions). That is, they are the same thing as function pointers. You can initialize a function pointer by giving it the name of a function.
The whole vector table is therefore declared as an array of function pointers, where each function has the signature void func (void). The *const declaration means that the function pointers themselves are read-only. Meaning they will get allocated in flash, as is proper for a vector table. Vector tables are usually allocated at a fixed, reserved address in flash.

“Strict aliasing”, named after the GCC optimization, is an assumption by the compiler that a value in memory will not be accessed through an lvalue of a type (the “declared type”) very different from the type the value was written with (the “effective type”). This assumption allows code transformations that would be incorrect if the possibility had to be taken into account that writing to a pointer to float could modify a global variable of type int.
Both GCC and Clang, extracting the most meaning out of a standard description full of dark corners, and having a bias for performance of generated code in practice, assume that a pointer to the int first member of a struct thing does not alias a pointer to the int first member of a struct object:
struct thing { int a; };
struct object { int a; };

int e(struct thing *p, struct object *q) {
  p->a = 1;
  q->a = 2;
  return p->a;
}

Both GCC and Clang infer that the function always return 1, that is, that p and q cannot be aliases for the same memory location:
e:
        movl    $1, (%rdi)
        movl    $1, %eax
        movl    $2, (%rsi)
        ret

As long as one agrees with the reasoning for this optimization, it should be no surprise that p->t[3] and q->t[2] are also assumed to be disjoint lvalues in the following snippet (or rather, that the caller causes UB if they alias):
struct arr { int t[10]; };

int h(struct arr *p, struct arr *q) {
  p->t[3] = 1;
  q->t[2] = 2;
  return p->t[3];
}

GCC optimizes the above function h:
h:
        movl    $1, 12(%rdi)
        movl    $1, %eax
        movl    $2, 8(%rsi)
        ret

So far so good, as long as one sees p->a or p->t[3] as somehow accessing a whole struct thing (resp. struct arr), it is possible to argue that making the locations alias would break the rules laid out in 6.5:6-7. Do (*p) and (*q) actually necessitate "access" (as the term is used in 6.5p7) to the arrays to which they point? (This isn't an entirely unreasonable standpoint; 6.5.2.1 Array Subscripting says that One of the expressions shall have type ‘‘pointer to complete object type’’, the other expression shall have integer type, and the result has type ‘‘type’’ - so the array lvalue has necessarily degraded to a pointer as per usual conversion rules; the only question is whether the array was accessed before the conversion occurred).
However, to defend the view that (*p)[3] is purely equivalent to *((int *)p + 3), we'd have to show that (*p)[3] doesn't require evaluation of (*p), or that if it does, the access does not have undefined behaviour (or defined but unwanted behaviour). if it points to an object, the result is an lvalue designating the

does this mean that the pointer must point to the start of the object? (It seems likely that this is what is meant).
