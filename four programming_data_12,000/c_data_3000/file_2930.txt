The number of merges remain same.While the number of merges remain the same, the pattern of merging actually makes the time complexity a lot worse. Assuming you have a merge() function to merge two sorted linked lists in O(n + m) time (where n = size of first list, m = size of second) and O(1) space, consider the following analysis in which I assume each list has on average n elements.

First merge will be O(n + n), as we're merging two n-sized lists
Second merge will be O(2n + n), as we're merging one n-sized list with our now 2n-sized list
Third merge will be O(3n + n)...and so on.

At this point we have to add up all of the additions inside the Big-Oh to get:
O(2n + 3n + 4n + 5n + ... + kn)

The sum of all these n terms is essentially n*(k(k+1))/2 because (k(k+1))/2 is the sum of the first k numbers. By taking the constant factors and lower order terms out of (k(k+1))/2, we can see that O((k(k+1))/2) = O(k^2), thus giving the algorithm O(n*k^2) time complexity.
I wrote a small article on this problem and analyzed further, the extent of the complexity differences. You should check it out here

To answer your other question on how does the divide and conquer approach actually yield O(nk*log(k)), think of how merge sort works.
If we have $n$ items, merge sort does n amount of work, as many times as it takes to pairwise merge n items together before they become one whole list. This number is log(n) (log base 2 of n), thus it takes a number of steps proportional to nlog(n) (again, realize we're doing n amount of work because there are always n elements at play, log(n) times). The reason merge sort has to break a list down into individual elements before merging them is because a single unit is the smallest thing we can get that is by definition, sorted, without us doing any work to sort it.
In our case, each list is already sorted, so we can treat each of the k lists (of size ~n) as an element sorted by definition. There is no need to break a sorted list down any further. Since there are k lists each with n elements, there will always be n*k elements at play. Luckily since each list is already sorted though, we only have to merge k "elements" together instead of all n*k list elements. So the same logic prevails, in that we have to merge k elements/lists together. In order for the compiler to generate the code for the template, it needs to see both the declaration and definition and therefore they both must be included in the .h file.

So it turns out it was user error!Identifying possibility of interferenceIn multi tasking environment. If a task has the expression y = x + x; is there a possibility of an interrupt(task switching) occurring between the two reads of x.In most cases a compiler generate code would read x only once since the optimisation is trivial.  In fact it might even translate the operation into a right-shift, equivalent to x << 1.  However you cannot guarantee that, and if x were declared volatile it would necessarily make two reads that will then be uninterruptible between reading of the low-order and high-order words (or vice versa),and in that case the assignment of y is also interruptable.
Another issue is that if x were not an atomic data type (i.e. could not be read in a single instruction) such as a 32 bit type on a 16 bit target for example, then even if it were a single read, it may be interruptable. 
In either case it is only normally a problem if the x itself (or y in the second case) is shared between contexts (in which case it should also be declared volatile so two reads would then be necessary), or if for some reason the timing of the assignment were somehow critical and needed to be entirely deterministic (unlikely).
If x is shared and therefore volatile but is an atomic type, the simple solution in this example is to write the expression y = x << 1 or y = x * 2 to ensure that x is read only once.  Where x is not atomic - you might need to lock the scheduler or disable interrupts (i.e. use a critical section), or more selectively protect the access with a mutex for example. For more complex expressions where the expression cannot be reduced to a single reference to the shared variable, simply assigning the variable to a non-shared local temporary variable ensures that it is read just once. void __declspec(naked) _cdecl _penter( void ) 
{
    __asm {
        push ebp;               // standard prolog
        mov ebp, esp;
        sub esp, __LOCAL_SIZE
        pushad;                 // save registers
    }

    unsigned int addr;
    // _ReturnAddress always returns the address directly after the call, but that is not the start of the function!
    // subtract 5 bytes as instruction for call _penter
    // is 5 bytes long on 32-bit machines, e.g. E8 <00 00 00 00>
    addr = (unsigned int)_ReturnAddress() - 5;

    if (addr == foo) printf ("foo() is called.\n");
    if (addr == bar) printf ("bar() is called.\n");

    _asm {
        popad;              // restore regs
        mov esp, ebp;       // standard epilog
        pop ebp;
        ret;
    }
}

The GC tracks the sizes of full userdata (and increases GC debt accordingly), but doesn't know them for light userdata.  If you 
lua_pushlightuserdata( L, ptr ); a value allocated elsewhere (by malloc, mmap, etc.), the GC "sees" a size of zero.  If you use lua_newuserdata( L, size ) for allocation, the GC knows the full size.
