    char buf[BUF_SIZE];

    assert(percent <= 100);

The fork() function does not block anything per se.  In particular, it returns as soon as it gets the new child process started, without waiting for the child to terminate.  Thus, unless the child is exceedingly short-lived, after a fork() returns successfully there are two processes running where there had been one.  This is the source of the name "fork".
Naturally, fork() is not instantaneous, and in fact it is likely to be somewhat expensive.  The thread that calls it cannot proceed until it returns, as those are the semantics of threads and function calls.  Other threads in the same process are not affected, and, as your other answer observes, they are not propagated to the new process, either.The term process in unix like operating systems, and its difference with a thread of execution is that all threads in a process share the same virtual space memory.  In other aspects, they are completely different running processes.  Each has it's own stack pointer (for user an kernel mode, as two threads can be simultaneously executing a system call, and have switched their stack to kernel stack, so there's a kernel stack per thread) so there's no reason for a system call in one thread to block or interrupt a system call in another  as it is possible for two different processes to be executing a system call simultaneously (except the obvious ones kill(2), read(2) or write(2), these last that block only if the two read's act upon the same file, which is locked during the time of the system call to serialize/sequence reads/writes to the same file)
Apart of these, the fork() call is a call that starts in one process, and ends in two.  So the fork() in the parent and the fork in the child behave as if both were started at the same time (in case you have a timestamp of the starting point of each call you will have the exact same timestamp, because the call was started only once, and the timestamp will need to be copied)  but as they have two different ends, these can be in any order, or with small difference or high (depending on the system load).  Nothing blocks a fork() except the allocation of the resources for the child to start (but when the child starts the parent can gone far away, or even died).  This can make the parent to continue after the fork() (but not as soon as the kernel knows if there are enough resources to build the child process, as the fork should give an error to the parent in case something goes wrong) quite early in the full system call, that remains building (with the new thread) the process table entry, the user area of the process, and the first thread of it, and returning 0 after that.
As you have been told, all thread related stuff is "copied" into the child, but as the child is not multithreaded, there are no threads to use that memory, but this is also not an issue, as while the process doesn't use it, it is not allocated (in pages of actual memory) actually (or it is allocated in swap space, if the parent decides to change it, using the Copy On Write feature)
The normal case of making a fork in a multithreaded process is when you need to execute another program.  In that case, fork() is going to be followed quickly by an exec() that will garbage collect all the unused memory. One of the more unexpected consequences of defining indexing as addition plus dereferencing is that because addition is commutative (i.e., p+i == i+p holds for all p, i), against all appearances indexing is a symmetrical operator, too: for all p[i] i[p] is a valid, equivalent expression:

    while (TRUE) {

        if (next == NULL) {
            break;
        }
        node = next;
    }

    return (node);

        if (root == NULL) {
            return (NULL);
        }
        node = hbt_find_leftmost(root);
        if (node) {
            return (node);
        }
    }

    node = hbt_node_next(current, &climb);

        node = hbt_find_leftmost(node);
    }
