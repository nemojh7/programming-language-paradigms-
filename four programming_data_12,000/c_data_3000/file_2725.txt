That is not how include files work. If you have a source file that has:
#include "a.h"
#include "b.h"

then this source file will see the definitions from a.h and b.h - in that order - but the header files themselves remain unaffected.
It is also generally accepted as a bad idea to have code that depends on the order of include files. Sometimes that is unfortunately unavoidable but such cases should be minimized and clearly explained. In your case, you should simply include fifo.h in uart.h, and your FIFO structure should be defined in fifo.h and not fifo.c. Explanation:

scanf() returns the number of successful conversions. If the user types a number, it is converted and stored into your_choice and scanf() returns 1, if the user enters something that is not a number, such as AA, scanf() leaves the offending input in the standard input buffer and returns 0, finally if the end of file is reached (the user types ^Z enter in windows or ^D in unix), scanf() returns EOF.
if the input was not converted to a number, we enter the body of the if statement: input is consumed one byte at a time with getchar(), until either the end of file or a linefeed is read.
if getchar() returned EOF, we have read the entire input stream, no need to prompt the user for more input, you might want to output an error message before returning an error code.
otherwise, set your_choice to -1, an invalid value so the read of the code complains and prompts for further input.

from what that I saw in comments, I reached to this conclusion that will end all discussions.
there are 3 different way for representing signed types. 

signed magnitude
1's complement 
2's complement

and in all of these representations, if the most significant bit is 1 then the number is negative and if it is 0 then the number is positive.
therefore, in this question, my computer uses 2's complement. As a result, 10010000 is a representation in 2's complement. its value is equal to the negative of 01110000=112, so the real result is -112.
however, when the type is unsigned, then the value of 400 must transfer to representation in binary but only there is enough space for 8 digits. Therefore, the representation will be 1001 0000 and since this is unsigned it is equal to 2^7+2^4=144.The type of the integer constant is int and when it is assigned to the type char, it is converted in an implementation-defined manner.
An implementation that satisfies your result works conceptually like this: add or subtract the range of the type (which is 256 in this case) from the value, until the value can be represented by the type.
Range of char in this case is: [-128,127] and 400 is not representable by type char.
Subtract 256, and the result 144 is still not representable.
